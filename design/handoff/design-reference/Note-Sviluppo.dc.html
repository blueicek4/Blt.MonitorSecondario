Note per lo sviluppo

React + TypeScript

Una SPA sola, servita dalla cassa, aperta in un browser in kiosk sul secondo monitor. Nessun router: lo schermo è una macchina a stati. Nessuna libreria di animazione: tutto CSS, perché il peggior PC cassa della base installata non regge un runtime JS che anima.

01

Macchina a stati, non pagine

idle
→
sale
→
payment
→
thanks
→ idle

message e offline non sono stati: sono livelli sovrapposti a qualunque stato. Un messaggio dalla cassa durante Satispay non deve smontare il QR, e la perdita di connessione non deve cambiare schermata — per questo nel modello sono due campi indipendenti e non rami dello stesso enum. È il punto dove una macchina a stati scritta male rovina tutto.

type DisplayPhase = 'idle' | 'sale' | 'payment' | 'thanks';

interface DisplayState {
  phase: DisplayPhase;
  lines: SaleLine[];          // ordine di battuta, append-only entro la vendita
  total: number;              // centesimi, mai float
  cover: number;              // coperti, per la riga di riepilogo
  payment?: PaymentRequest;   // presente solo in phase 'payment'
  message?: CashierMessage;   // livello sovrapposto, a tempo
  lastItemPhoto?: string;     // url foto dell'ultimo articolo battuto
  link: 'online' | 'stale' | 'lost';
}

Gli importi sono interi in centesimi. Non negoziabile: un totale calcolato in number decimale su un monitor che il cliente guarda mentre paga è un reclamo che arriva. Formattazione solo in output, con Intl.NumberFormat('it-IT', { style: 'currency', currency: 'EUR' }), e link: 'stale' è lo stato intermedio fra online e perso: nessun dato da 8 secondi ma il socket è ancora aperto.

Perché il footer sta fuori
Se BluetechFooter vivesse dentro StateLayer, ogni transizione lo farebbe sfarfallare e un tema potrebbe nasconderlo cambiando il contenitore. Fuori, è strutturalmente sempre a schermo: il requisito commerciale diventa un fatto architetturale, non una regola da ricordare.
Finestra scorrevole, non virtual list
Con 30+ righe si mostrano solo le ultime N che entrano nello spazio disponibile, calcolate da altezza riga e altezza card. Nessuna virtualizzazione: la lista cresce di una riga per volta, e una libreria di virtual scroll su grafica integrata costa più di quanto risolva.
03

Messaggi dalla cassa

type SaleLine =
  | { kind: 'item';     id: string; desc: string; qty: number; amount: number; photo?: string }
  | { kind: 'discount'; id: string; desc: string; amount: number }   // amount < 0
  | { kind: 'surcharge';id: string; desc: string; amount: number }   // amount > 0
  | { kind: 'void';     id: string; desc: string; amount: number; voidsId?: string }
  | { kind: 'note';     id: string; text: string };

type CashIn =
  | { t: 'sale.open' }
  | { t: 'sale.line';   line: SaleLine }
  | { t: 'sale.total';  total: number; cover: number }
  | { t: 'sale.close' }
  | { t: 'display.msg'; text: string; ttl?: number }
  | { t: 'pay.qr';      provider: 'satispay'; png: string; amount: number }
  | { t: 'pay.clear' }
  | { t: 'cfg';         theme: ThemeTokens; ads: AdSlide[]; ticker?: string };
Regole di robustezza
  • Il totale arriva dalla cassa, non si somma lato monitor. Se la somma delle righe non torna, vince la cassa e si logga la discrepanza: la cassa è la fonte fiscale.
  • Ogni riga ha un id stabile, così lo storno può puntarla e React non rimonta l'intera lista a ogni messaggio (key = id, mai l'indice: con l'indice l'animazione di ingresso scatta sulla riga sbagliata).
  • pay.qr.png è un data URI o un percorso locale servito dalla cassa. Si disegna a dimensione multipla intera del lato in moduli, con image-rendering: pixelated: un QR interpolato è un QR che il telefono non legge.
  • Nessun messaggio di esito pagamento esiste nel protocollo, quindi l'interfaccia non lo promette. Lo stato payment finisce solo con pay.clear, sale.close o un altro messaggio.
  • Messaggi fuori sequenza (una sale.line senza sale.open) aprono implicitamente la vendita invece di essere scartati: in sala un monitor vuoto è peggio di un monitor con un dato in più.
04

Token come variabili CSS

interface ThemeTokens {
  cPrimary: string; cSecondary: string; cAccent: string;
  cBg: string; cSurface: string; cText: string; cMuted: string; cOnPrimary: string;
  fontDisplay: string; fontText: string;
  radius: number;                                  // 0–32 px
  bgStyle: 'solid' | 'gradient' | 'mesh' | 'image' | 'video';
  bgAsset?: string;
  glass: number;                                   // 0–100
  motion: 'full' | 'light' | 'eco';
  mode: 'day' | 'night' | 'auto';                  // 'auto' = sugli orari di apertura
  qrLayout: 'fullscreen' | 'beside';               // il QR a tutto schermo, o accanto al conto
  footerVariant: 'light' | 'dark';                 // l'unica scelta sul footer Bluetech
}

// Ogni tema è una COPPIA di palette con gli stessi nomi di token.
// Non si deriva la variante giorno schiarendo la notte: i due set sono
// progettati separatamente, perché i primari vanno scuriti per tenere
// il bianco sopra sopra 4,5:1. 'auto' interpola solo il cambio (900 ms,
// curva uscita) e non tocca mai layout o dimensioni.

// DisplayRoot: i token diventano custom properties, i derivati si calcolano una volta
const styleVars = {
  '--c-primary': t.cPrimary,
  '--c-surface': t.cSurface,
  '--radius': `${clamp(t.radius, 0, 32)}px`,
  '--glass-alpha': String(t.glass * 0.0012),
  '--glass-blur': `${t.glass * 0.28}px`,
} as React.CSSProperties;
Il pannello non può rompere la leggibilità
Prima di scrivere i token, il pannello del locale calcola il contrasto di cText su cBg e di cOnPrimary su cPrimary. Sotto 4,5:1 non salva: propone la correzione più vicina. Lo stesso controllo gira anche all'avvio del monitor, perché un tema può arrivare da un backup vecchio.
Font locali, non CDN
Solo famiglie open source con licenza che consente l'incorporazione, servite come woff2 dalla cassa con font-display: swap e un fallback di sistema a metriche vicine. Il monitor deve partire identico con il router staccato.

Come si implementano le animazioni

:root {
  --e-spring: cubic-bezier(.22, 1.2, .36, 1);
  --e-out:    cubic-bezier(.16, 1, .3, 1);
  --e-move:   cubic-bezier(.33, 1, .68, 1);
  --d-row: 420ms; --d-total: 520ms; --d-state: 520ms;
}
[data-motion='light'] { --d-row: 300ms; --d-total: 320ms; --d-state: 320ms; --e-spring: var(--e-out); }
[data-motion='eco']   { --d-row: 160ms; --d-total: 140ms; --d-state: 160ms; }

@media (prefers-reduced-motion: reduce) { /* forza il ramo eco, token ignorato */ }
Odometer
Il totale si spezza in caratteri. Ogni cifra è uno <span> con overflow: hidden alto 1em che contiene una colonna 0…9; si imposta transform: translateY(-Ndigit em) e si lascia animare la transizione. Le cifre identiche fra vecchio e nuovo valore non ricevono una nuova key, quindi non si muovono. Nel livello eco il contenitore passa a transition: none e si incrocia solo l'opacità.
Elemento condiviso fra stati (FLIP)
Un hook useFlip(ref, deps): getBoundingClientRect() prima del cambio di fase, confronto dopo il commit in useLayoutEffect, applicazione del delta come transform e rimozione nel frame successivo con la transizione attiva. Vale solo per TotalBlock. Nei livelli Leggera ed Eco l'hook ritorna subito e si usa la dissolvenza: una transizione condivisa a 30 fps è peggio di nessuna transizione.
Playlist e memoria
Due slot sovrapposti che si alternano. La slide successiva si decodifica con decode() prima di entrare, così la dissolvenza non parte su un'immagine non pronta. I video si montano uno per volta, muted, playsInline, preload="auto"; will-change si aggiunge all'inizio dell'animazione e si toglie alla fine, mai in modo permanente.
06

Formato, kiosk, resilienza

Il layout si adatta, non scala
Tre varianti scelte da container query sul rapporto d'aspetto: wide (≥ 1,5 — scontrino più colonna laterale), narrow (fra 1,2 e 1,5 — scontrino pieno, totale sotto la lista, colonna laterale via), portrait (< 1 — pubblicità sopra, scontrino sotto). Le dimensioni del testo vengono da una tabella discreta per fascia, non da vw: con vw su 1024×768 il totale diventa più piccolo che su 1280×800, che è esattamente il contrario di quello che serve.
Il QR segue la stessa logica: con qrLayout: 'beside' su una variante wide lo scontrino passa da 1180 a 760 px e il QR occupa lo spazio delle promozioni a 488 px di lato; su narrow e portrait il token viene ignorato e il QR va a tutto schermo, perché non c'è colonna laterale da cui prendere lo spazio. Il minimo non negoziabile è 1/3 dell'altezza schermo.
Kiosk
Chromium --kiosk --app sul display secondario, cursore nascosto, blocco di menu contestuale, selezione e zoom da tastiera. Riavvio automatico della pagina se il socket non torna in 60 s. Nessuno alert né confirm da nessuna parte: in kiosk un dialogo blocca lo schermo e nessuno in sala sa cosa fare.
Se la cassa tace
8 s senza messaggi → stale, compare la pillola, l'ultima schermata resta intatta. Nessuno svuotamento, nessuna schermata d'errore, nessun ritorno all'Attesa: se il cliente stava guardando un QR, quel QR resta. Riconnessione con backoff 1-2-4-8 s fino a 15 s, e alla ripresa la cassa rimanda lo stato completo invece di un delta.
Diagnostica
Il monitor tiene un anello degli ultimi 200 messaggi e le metriche fps, interrogabili dalla cassa. Serve al supporto per rispondere a “il monitor non si aggiorna” senza andare sul posto, ed è l'unico modo per sapere quali installazioni hanno degradato da sole il livello di animazione.
07

Cosa manca per implementare

Il protocollo qui sopra è una proposta, non una lettura del comportamento reale della cassa. Prima di scrivere codice servono quattro risposte:
  • Come la cassa espone i dati al monitor oggi — socket, HTTP locale, file, o il protocollo del visore seriale incapsulato.
  • Se il flusso delle righe è un vero delta o una ristampa completa dello scontrino a ogni battuta: cambia tutta la logica delle animazioni di ingresso.
  • Se le foto articolo esistono già nell'anagrafica e con che nome si risolvono.
  • Se esiste un evento affidabile di fine vendita distinto dal totale, perché da quello dipende se lo stato Grazie si può mostrare sempre o solo quando la cassa lo dice.
Il logo Bluetech e quello Satispay nei mockup sono segnaposto: il primo va sostituito con l'SVG ufficiale, il secondo con l'asset preso dal brand kit Satispay, rispettando clearspace e colori delle loro linee guida. Nessuno dei due è stato ridisegnato qui.
